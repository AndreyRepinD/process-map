# In.Plan Process Map

Интерактивная карта E2E-процесса планирования поставок: обзор из 4 этапов и детализация
шагов каждого этапа с входами, выходами и интеграциями (DP, PS, IO, ERP, MRP). Статический
бандл на Vite + React + React Flow, без бэкенда, предназначен для встраивания в страницу
вики In.Plan через `iframe`.

- Требования и сценарии — [PRD.md](PRD.md).
- Техническая спецификация (модель данных, экраны, поведение) — [SPEC.md](SPEC.md).
  При расхождении PRD и SPEC главнее SPEC.
- Правила разработки и работа с трекером `bd` — [CLAUDE.md](CLAUDE.md).

Источник истины по содержанию процесса — `src/data/snp/process.json`. Приложение не ходит
в сеть: все шрифты и иконки лежат внутри бандла.

## Сборка и запуск

Node ≥ 22.6 (в репозитории зафиксирован `22.14.0` в `.nvmrc`), npm.

```bash
npm i                # установка зависимостей

npm run dev          # dev-сервер, http://localhost:5173
npm run check        # tsc --noEmit + eslint + vitest (обязателен перед закрытием задачи)
npm run e2e          # Playwright e2e
npm run build        # продакшен-сборка в dist/
npm run preview      # локальный просмотр собранного dist/

npm run layout       # пересчитать стартовые координаты узлов (dagre) → process.json
npm run data         # весь конвейер данных: импорт из pptx → раскладка → process.json
#   обе команды принимают карту:  npm run data -- --map snp
```

`npm run layout` и `npm run data` запускаются как
`node --experimental-strip-types scripts/*.ts`, то есть **требуют Node ≥ 22.6** —
на более старой версии флага `--experimental-strip-types` нет и скрипт не стартует.
`npm run layout` детерминирован: повторный прогон на тех же данных даёт побайтово
тот же файл. Он меняет в JSON **только** поле `position` у узлов; содержание
(id, label, рёбра, группы, типы) не трогает. `npm run data` — это
`scripts/import-pptx.py` и следом `npm run layout`, склеенные в одну команду,
потому что порядок между ними обязателен, а поодиночке его никто не обязан
помнить. Подробности, чем плох одиночный импорт и как это обнаруживается — см.
[Данные](#данные).

`dagre` (`@dagrejs/dagre`) — только devDependency скрипта раскладки, в рантайм-бандл
не попадает (SPEC §1).

## Трекер задач и `.beads/issues.jsonl`

Трекер `bd` хранит задачи в embedded Dolt (`.beads/embeddeddolt/`) — каталог в `.gitignore`,
в репозиторий не попадает. Единственная переносимая копия истории задач, включая обоснования
из `bd close --reason` (в них — существенная часть решений по проекту), — `.beads/issues.jsonl`.

Чтобы этот файл не устаревал незаметно, экспорт настроен автоматическим штатными средствами
`bd` (`.beads/config.yaml`: `export.auto: true`, `export.git-add: true`, `export.interval: 60s`):
любая пишущая команда `bd` (`close`, `update`, `config set` и т. п.) сама переэкспортирует
`.beads/issues.jsonl` и добавляет его в индекс git — throttled интервалом, так что на каждый
коммит это не нагрузка. Git-хук `.beads/hooks/pre-commit` (штатный механизм `bd hooks install`,
файлы отслеживаются репозиторием) подстраховывает перед самим коммитом, если что-то из
`.beads/` уже застейджено. Хук никогда не роняет коммит: если `bd` не найден в `PATH` —
предупреждает и пропускает шаг; если вызов `bd` упал или завис — тоже не блокирует
(таймаут `BEADS_HOOK_TIMEOUT`, по умолчанию 300 c).

**После клонирования репозитория выполните один раз:**

```bash
bd hooks install --beads
```

Сам хук лежит в `.beads/hooks/` и приезжает с клоном, но какой каталог git считает
хуками (`core.hooksPath`) — локальная настройка `.git/config`, привязанная к пути
на конкретной машине; в свежем клоне её нет, `bd hooks install --beads` проставляет
её заново (идемпотентно, безопасно перезапускать). После этого `bd bootstrap`
поднимет базу из `.beads/issues.jsonl`, если базы ещё нет.

## Что попадает в `dist/`

`vite.config.ts` содержит `base: './'` — приложение должно работать из произвольного
подкаталога хоста. **Эту настройку менять нельзя**: на ней держится всё встраивание.

После `npm run build` в `dist/` лежат:

```
dist/index.html
dist/assets/index-*.js       # ~485 KB, ~146 KB gzip
dist/assets/index-*.css      # ~62 KB, ~10 KB gzip
dist/assets/open-sans-*.woff2  # 9 файлов Open Sans (latin / cyrillic / cyrillic-ext × 400/600/700)
```

Что здесь важно и что стоит перепроверять при обновлении зависимостей:

- В `dist/index.html` ссылки на ассеты относительные — `./assets/...`, без ведущего слэша.
- Шрифт Open Sans поставляется пакетом `@fontsource/open-sans` и собирается в `dist/assets/`.
  Ссылок на `fonts.googleapis.com` / `fonts.gstatic.com` в сборке нет — это принципиально:
  корпоративный контур может не иметь доступа к внешним CDN, а CSP родительской страницы
  почти наверняка их не разрешит.
- Иконки (`src/assets/icons/*.svg`, 14 штук) не выкладываются отдельными файлами, а
  инлайнятся в JS как `data:image/svg+xml` — все они меньше лимита Vite
  `build.assetsInlineLimit` (4096 байт). Самая большая, `recalculation.svg`, весит 3815 байт,
  то есть запас невелик: если иконку заменят на более тяжёлую, она превысит лимит и
  превратится в отдельный сетевой запрос `dist/assets/*.svg`. Это не сломает приложение,
  но добавит запрос, который может не пройти CSP родительской страницы. Проверка:
  `find dist -name '*.svg'` должен ничего не находить.

Быстрая проверка сборки:

```bash
npm run build
grep -oE '(src|href)="[^"]*"' dist/index.html   # ожидается только ./assets/...
grep -rE 'fonts\.(googleapis|gstatic)\.com' dist/   # ожидается пусто (exit 1)
find dist -name '*.svg'                          # ожидается пусто
ls dist/assets/*.woff2                           # шрифт внутри dist
```

## Развёртывание на GitHub Pages

Карта раздаётся статикой с GitHub Pages:

**https://igordikinov.github.io/process-map/**

Публикация автоматическая: `.github/workflows/deploy.yml` на каждый push в `main`
запускает параллельно два job'а — `build` (`npm run check`, затем сборка `dist/`) и
`e2e` (`npm run e2e` в chromium). Деплой ждёт оба: сломанное на Pages не попадёт
ни из-за красных проверок, ни из-за красных e2e. Ручной запуск — через
`workflow_dispatch` во вкладке Actions.

Тот же workflow гоняет `build` и `e2e` на каждый pull request, но без деплоя:
job `deploy` пропускается, артефакт для Pages не выгружается, а права на
публикацию выданы точечно только ему. Проверки специально не вынесены в
отдельный workflow — два независимых workflow не знают друг о друге, и деплой
уехал бы даже при красных проверках.

При падении e2e отчёт Playwright и трейсы выгружаются артефактом
`playwright-report` (хранится 7 дней) — по нему разбирают прогон, не воспроизводя
его локально.

**Однократная настройка в репозитории:** Settings → Pages → Source: **GitHub Actions**.
Без этого workflow будет падать на шаге деплоя.

Публикуется только собранный `dist/`. Исходники, презентация и макет остаются
в репозитории, но сайтом не раздаются — хотя репозиторий публичный, и содержимое
процесса в бандле по этому адресу доступно всем.

Что Pages даёт бесплатно из трёх условий ниже:

| Условие                       | На GitHub Pages                                                 |
| ----------------------------- | --------------------------------------------------------------- |
| Завершающий слэш (условие 1)  | закрыто: Pages отдаёт `301` с `/process-map` на `/process-map/` |
| Только https (условие 3)      | закрыто: Pages работает только по https                         |
| `X-Frame-Options` (заголовки) | Pages его не отдаёт, встраивание в iframe не блокируется        |

Остаётся **условие 2** — атрибуты `sandbox` у самого `<iframe>`. Это сторона вики,
хостинг на него не влияет. И заголовки Pages не настраиваются: собственную CSP
для домена карты задать нельзя.

## Встраивание в In.Plan

Пример из SPEC §6:

```html
<iframe
  src="https://<host>/process-map/?stage=1"
  style="width:100%;height:720px;border:0"
  loading="lazy"
></iframe>
```

Ширина и высота задаются контейнером: приложение занимает 100 % фрейма и перестраивается
через `ResizeObserver` при изменении размера. Атрибут `allow="clipboard-write"` из раннего
черновика SPEC не нужен — в v1 приложение с буфером обмена не работает.

Ниже — три условия работоспособности. Это не пожелания: при нарушении любого из них
карта либо не загрузится вовсе, либо будет отказывать молча, без сообщения об ошибке.

### Условие 1. Завершающий слэш в URL обязателен

`src` должен указывать на `https://<host>/process-map/` — **со слэшем на конце**
(или сразу на `.../process-map/index.html`).

Почему. При `base: './'` файл `index.html` ссылается на `./assets/...` — относительно URL
документа, а не относительно каталога. Если страница отдана по адресу `/process-map`
(без слэша), браузер разрешит `./assets/index-*.js` в `/assets/index-*.js`, то есть
в корень хоста, и получит 404. Отвалится не иконка и не шрифт, а **сам бандл**: фрейм
останется пустым белым прямоугольником. Разница ровно такая:

```
http://host/process-map      ->  http://host/assets/index-CTQNOulP.js      (404)
http://host/process-map/     ->  http://host/process-map/assets/index-CTQNOulP.js  (ok)
```

Приложением это не лечится (задача `process-map-phd`, проверено фактически на статическом
сервере). Лечение только на стороне хостинга: **редирект 301 с `/process-map` на
`/process-map/`**. Большинство веб-серверов делает это по умолчанию для каталогов
(nginx `autoindex`/`try_files`, Apache `DirectorySlash`), но не все статические хостинги
и не все реверс-прокси — требование нужно проверить на конкретном стенде, а не считать
данностью.

### Условие 2. `sandbox` без `allow-popups` не даст открыть экран

Кнопка «Открыть в модуле» и иконка ссылки на шаге открывают экран In.Plan через
`window.open(url, '_blank')` (`src/utils/url.ts::openScreen`, SPEC §4.8) — то есть **в новой
вкладке**. Страница вики остаётся на месте.

Требование к встраивающей стороне — одно из:

- не использовать `sandbox` вовсе (штатный вариант для собственного статического бандла), **или**
- добавить `allow-popups` (без него новая вкладка не откроется), а также `allow-scripts` и
  `allow-same-origin` — без последнего недоступен `localStorage`, то есть отвалятся правки ссылок;
  сама карта при этом работает, проверено. Плюс `allow-downloads`, иначе «Экспорт JSON» (§4.4)
  молча не сработает: он идёт через `<a download>`, и без флага браузер блокирует скачивание.

Все три конфигурации — без `sandbox`, с полным набором и без `allow-popups` — проверяются
автоматически: `e2e/iframe-sandbox.spec.ts` поднимает карту в настоящем `<iframe>` и смотрит,
открылась ли вкладка. До этого требование было обещанием, которое ничем не проверялось.

Отказ здесь, в отличие от прежнего поведения, **наблюдаем**: заблокированный `window.open`
возвращает `null`. Это не превращается в сообщение пользователю (текста для него в SPEC нет),
но отличимо в отладке — и это главная причина, по которой цель поменяли.

<details>
<summary>Почему раньше было иначе и что пошло не так (<code>process-map-6ap</code>)</summary>

До 31.08.2026 ссылка целилась в `'_top'` — переводила всю родительскую страницу, — а при
недоступном `window.top` откатывалась на `'_blank'`. Проблема была в том, как определялась
недоступность: `openScreen` читал `top.document`. Для чужого origin это бросает `SecurityError`
**всегда**, а карта живёт на чужом origin по построению (она на GitHub Pages, вики — на своём
домене). То есть `'_top'` не выполнялся никогда, «фолбэк» был единственным поведением, и этот
раздел вместе с чек-листом приёмки описывал исход, которого не бывает.

Проба путала две разные вещи: **доступ к документу** верхнего фрейма (кросс-доменно запрещён
всегда) и **право увести** этот фрейм (по клику обычно разрешено). Вдобавок у `'_top'` был
неустранимый изъян: `sandbox` без `allow-top-navigation` отказывает **без исключения** — молча,
и перехватить это нечем.

Решением владельца поведение приведено к тому, что и так происходило: новая вкладка.

</details>

Если когда-нибудь понадобится, чтобы страница вики уходила на экран, это по-прежнему возможно:
переключить `linkTarget` в `src/config.ts` на `'_top'` и пересобрать. Но только вместе с
проверкой на стенде — автоматического отката больше нет, и при `sandbox` без
`allow-top-navigation` кнопка молча перестанет работать.

### Условие 3. Только https

Хостинг карты обязан отдавать её по https с валидным сертификатом. Вики In.Plan работает
по https, и http-фрейм внутри https-страницы браузер блокирует как mixed content —
фрейм просто не отрисуется (PRD §9). Сюда же относятся ссылки на экраны: в редакторе
`https://` — норма, `http://` сохраняется с предупреждением (SPEC §4.4), но в реальном
встраивании http-ссылка на экран приведёт к тому же блоку.

### Заголовки: CSP и X-Frame-Options

Отвечает сервер, на котором лежит `dist/`:

- **`X-Frame-Options: DENY` отдавать нельзя** — с ним встраивание невозможно в принципе.
  `SAMEORIGIN` подходит, только если карта и вики на одном origin.
- Вместо этого — `Content-Security-Policy: frame-ancestors https://<домен-вики>`
  (например `frame-ancestors https://*.company.ru`), чтобы разрешить встраивание именно
  вики и никому больше. `frame-ancestors` имеет приоритет над `X-Frame-Options`
  в современных браузерах, но старый заголовок лучше просто убрать, а не полагаться
  на приоритет.
- CSP **родительской страницы** тоже должна разрешать наш origin в `frame-src`
  (или `default-src`). Приложение самодостаточно (нет внешних шрифтов, картинок и
  запросов), но использует инлайновые стили React Flow, поэтому в собственной CSP карты
  `style-src` должен допускать `'unsafe-inline'`, а `img-src` — `data:` (иконки).

## Deep-link

Карта читает параметры строки запроса (SPEC §4.7):

| Параметр     | Значение                  | Что делает                                     |
| ------------ | ------------------------- | ---------------------------------------------- |
| `?stage=2`   | номер этапа 1..4          | открывает сразу уровень 2 нужного этапа        |
| `&node=<id>` | id узла из `process.json` | открывает этап этого узла и его боковую панель |

`id` узлов уникальны глобально, поэтому `?node=<id>` работает и без `stage`; при конфликте
выигрывает этап, которому принадлежит узел. Несуществующий этап или узел не роняет
приложение — открывается обзор (уровень 1).

При навигации внутри карты URL переписывается через **`history.replaceState`, а не
`pushState`**. Это сделано намеренно: карта живёт в iframe, и `pushState` засорял бы историю
родительской страницы вики — кнопка «Назад» в браузере переставала бы работать так, как
ожидает пользователь. Побочный эффект, о котором стоит знать: адрес самой вики при этом
не меняется, так что «скопировать ссылку на текущий шаг» из адресной строки браузера
не получится — deep-link собирается вручную.

## Данные

- **`src/data/snp/process.json` — источник истины.** Схема описана в SPEC §3, валидируется
  zod-схемой `src/data/schema.ts`, контрактом карты `tests/mapContract.test.ts` (схема,
  целостность рёбер, конвейер доведён до конца — проверяется для каждой карты в
  `src/data/*/`) и `tests/snp/content.test.ts` (полнота списка шагов именно этой карты).
- Содержание переносится из презентации скриптом
  `scripts/import-pptx.py` (python-pptx). Скрипт детерминирован, id стабильны — на них
  завязаны deep-link и ключи `localStorage`.
- Координаты узлов пересчитывает `scripts/layout.ts` (`npm run layout`, dagre).
- **Какая карта собирается** — переменная `MAP` (по умолчанию `snp`), см. SPEC §3
  «Выбор карты на сборке». Единственная точка выбора — `scripts/mapTarget.ts`;
  `src/data/loader.ts` импортирует данные через алиас `@map` и не знает, какая
  это карта. Тот же набор карт разбирают команды данных: `npm run data -- --map snp`.
- `npm run build` собирает **все четыре** карты в один `dist/`: SNP в корень,
  MRP в подкаталог `mrp/`, DP в `dp/`, MEIO в `meio/`. Порядок в скрипте
  обязателен — сборка карты по умолчанию чистит `dist` целиком. Локально карты
  показывают `npm run dev:mrp` (порт 5174), `npm run dev:dp` (5175),
  `npm run dev:meio` (5176).
- Раздача: `https://<host>/process-map/` (SNP), `.../process-map/mrp/`,
  `.../process-map/dp/`, `.../process-map/meio/`. Слэш на конце обязателен для
  каждого подкаталога — без него относительные пути к ассетам разрешаются
  относительно родителя, и страница подтягивает бандл чужой карты.
- Карты `dp` и `meio` собираются со **сгенерированного** слайда:
  `scripts/author/<map>.json` (содержание владельца, заморожено) →
  `python scripts/author/<map>.py` → `In.Plan <MAP> process <дата>.pptx` →
  `npm run data -- --map <map>`. Правится JSON, а не pptx и не process.json.
  Сверка этих карт с BPMN-моделью — `docs/reconciliation/dp-meio-bpmn.md`.

### Что нужно установить для `npm run data`

Импортёру нужен Python с `python-pptx` и `lxml` — в `package.json` их нет и быть
не может, это другой пакетный менеджер:

```bash
python3 -m venv .venv && .venv/bin/pip install python-pptx lxml
PYTHON=.venv/bin/python npm run data -- --map snp
```

Переменная `PYTHON` нужна не только для venv: `scripts/data.ts` пробует `python`
и `py`, а на macOS с Homebrew в PATH обычно только `python3`.

### `npm run data` — единственный правильный способ пересобрать данные

Конвейер состоит из двух шагов, и порядок между ними обязателен:

1. `scripts/import-pptx.py` вынимает содержание из презентации и кладёт в `position`
   **сырую геометрию слайда** — на ней карточки накладываются друг на друга
   (157 пересекающихся пар узлов на актуальной презентации);
2. `scripts/layout.ts` (`npm run layout`) считает по этой геометрии пригодные
   координаты через dagre и перезаписывает `position`.

`npm run data` (`scripts/data.ts`) запускает оба шага в правильном порядке одной
командой. Раньше порядок нужно было помнить самому: тот, кто прогонял только
импорт и коммитил результат, получал карту с наложенными друг на друга карточками.
**Если поменялась презентация — только `npm run data`, никогда не
`python scripts/import-pptx.py` сам по себе.**

Если одиночный импорт всё же попал в закоммиченный `process.json`, это не остаётся
незамеченным: `npm run check` падает на каждом узле в `tests/layout.test.ts`
с сообщением

```
Похоже, прогнан только импорт (scripts/import-pptx.py) — в файле сырая
геометрия презентации, на которой карточки накладываются.
Конвейер целиком: npm run data
```

а сам импортёр в этом случае завершает вывод блоком «КОНВЕЙЕР НЕ ЗАВЕРШЁН —
ОБЯЗАТЕЛЬНО: npm run layout» (если его запустили не из конвейера) либо
«ШАГ 1 ИЗ 2 ГОТОВ — ДАЛЬШЕ РАСКЛАДКА» (когда его вызвал `npm run data` — раскладка
в этом случае стартует сразу следом).

**Почему не `python scripts/import-pptx.py && npm run layout` в package.json.**
Импортёр возвращает код **2**, когда потерял ручную ссылку на экран (её узел
пропал из презентации), — при этом `process.json` уже записан корректно, и
раскладку всё равно нужно прогнать. `&&` в этом случае молча оборвал бы конвейер
на сыром, непригодном к показу файле. `scripts/data.ts` пробрасывает код 2
наружу (потерянные ссылки по-прежнему нужно проставить заново, см.
[docs/ссылки-на-экраны.md](docs/ссылки-на-экраны.md)), но раскладку выполняет
в любом случае.

### `slidePosition` — служебное поле, не удалять

У узлов есть необязательное поле `slidePosition` — исходная геометрия слайда,
которую пишет импортёр и не трогает раскладка. `npm run layout` берёт из него
порядок узлов и деление data-узлов на колонки входов/выходов; поле `position`
раскладка только перезаписывает и никогда из него не читает.

Так было не всегда: раньше раскладка сидировалась самим `position` — то есть
результатом собственного предыдущего прогона. После первого запуска геометрия
презентации оказывалась потеряна, и очередной пересчёт опирался уже не на
презентацию, а на себя самого. `slidePosition` эту зависимость разрывает: он
всегда остаётся геометрией слайда и никем, кроме импортёра, не перезаписывается.

Поле опционально и в UI не используется, но должно оставаться в
`src/data/schema.ts` — иначе zod вычистит его при экспорте
(`src/utils/processTransfer.ts::serializeProcessMap`), и файл, скачанный через
«Экспорт JSON» в редакторе, перестанет побайтово совпадать с версией в
репозитории.

Изменение содержания процесса (шаги, связи, группы) — это правка презентации и
`npm run data`, а не ручное редактирование JSON и не догадка. Спорные места
заводятся задачей в `bd` с типом `question`.

## Правки ссылок: режим редактора

> **Пошаговая инструкция — [docs/ссылки-на-экраны.md](docs/ссылки-на-экраны.md).**
> Там весь путь целиком: как проставить ссылки, как выгрузить их в репозиторий,
> что происходит при перегенерации данных из презентации и что делать, если узел
> из неё исчез. Ниже — только устройство механизма.

Переключатель «Просмотр / Редактор» в тулбаре. В режиме «Редактор» у каждого узла в боковой
панели доступна форма «Название экрана» + «Ссылка» (валидация: `https://` — норма,
`http://` — с предупреждением, остальные протоколы отклоняются), кнопки «Сохранить»,
«Отмена», «Удалить ссылку». В тулбаре появляются «Экспорт JSON», «Импорт JSON»,
«Сбросить правки».

Режим не запоминается: после перезагрузки всегда «Просмотр» (SPEC §4.4).

**Правки живут только в браузере конкретного пользователя.** Они хранятся в `localStorage`
под ключом карты `inplan-process-map:snp:overrides:v1` и накладываются поверх JSON при старте
(`src/data/loader.ts`). Из этого следует:

- ссылки, проставленные методологом, **не видны другим пользователям** и **не попадают
  в репозиторий сами по себе**;
- чтобы зафиксировать их для всех, нужно нажать **«Экспорт JSON»** (скачивается
  `process.json` с уже слитыми правками) и положить полученный файл в
  `src/data/snp/process.json`, после чего пересобрать и выложить `dist/`;
- «Импорт JSON» принимает такой же файл и заменяет им локальные правки — это способ
  передать наработки другому человеку до того, как они попали в репозиторий;
- очистка данных сайта в браузере или другой браузер/профиль = правки потеряны.
  Экспортировать стоит регулярно, а не «когда закончу».

## Чек-лист приёмки на стенде In.Plan

Проходится владельцем процесса на реальной странице вики после выкладки `dist/`
(задача `process-map-dfr`). Каждый пункт сформулирован так, чтобы **исправную работу
нельзя было спутать с тихим отказом** — большая часть проблем встраивания проявляется
не ошибкой, а тем, что «ничего не произошло».

Подготовка: откройте DevTools (F12), вкладки **Console** и **Network**, и держите их
открытыми весь проход. Пустая консоль — часть критерия приёмки (PRD §8).

### 1. Загрузка в iframe

- [ ] **Сделать:** открыть страницу вики с встроенной картой.
- [ ] **Ожидается:** во фрейме видна карта — верхняя полоса с заголовком и бейджем
      «4 этапа», серое полотно в точку, 4 карточки этапов, легенда.
- [ ] **Тихий отказ:** фрейм есть, но внутри белый (или серый) пустой прямоугольник,
      никаких ошибок на странице. Это загрузка бандла. Смотреть **Network**: если есть
      404 на `assets/index-*.js` — переходите к пункту 3 (слэш) и пункту 4 (https);
      если запроса к `assets/*` нет вовсе — фрейм заблокирован, смотрите Console на
      сообщения про `X-Frame-Options` / `frame-ancestors` / mixed content.
- [ ] **Ожидается:** в Console нет красных ошибок.

### 2. Что запрашивается по сети

- [ ] **Сделать:** в Network отфильтровать по домену, отличному от домена карты.
- [ ] **Ожидается:** запросов на сторонние домены нет вообще — ни `fonts.googleapis.com`,
      ни `fonts.gstatic.com`. Все запросы: `index.html`, один `.js`, один `.css`
      и файлы `open-sans-*.woff2` с нашего же хоста.
- [ ] **Тихий отказ:** карта отрисовалась, но текст выглядит системным шрифтом,
      а в Network висит красный запрос к внешнему домену — CSP вики режет внешние
      ресурсы. Значит, в сборку просочилась внешняя зависимость: это дефект сборки,
