## 3. Модель данных (`process.json`)

```ts
type NodeType = 'step' | 'data' | 'integration' | 'warning';
type SystemCode = 'DP' | 'PS' | 'IO' | 'ERP' | 'MRP' | 'INPLAN' | 'BI' | 'EPM';

interface ScreenLink {
  title: string; // «Планирование поставок › Объёмный план»
  url: string; // https://...
}

interface ProcessNode {
  id: string; // kebab-case, уникален глобально
  type: NodeType;
  label: string; // ≤ 2 строки
  description?: string;
  group?: string; // id группы (dashed-контейнер), напр. "unconstrained"
  direction?: 'in' | 'out'; // колонка data-узла: вход или выход этапа
  inputs?: string[]; // человекочитаемые
  outputs?: string[];
  system?: SystemCode;
  owner?: string;
  screen?: ScreenLink;
  position: { x: number; y: number }; // что показывает приложение (считает layout.ts)
  slidePosition?: { x: number; y: number }; // исходная геометрия слайда (пишет import-pptx.py)
}

interface Group {
  id: string;
  label: string;
}

interface Edge {
  id: string;
  source: string;
  target: string;
  kind: 'process' | 'integration' | 'data';
  label?: string;
}

interface ExternalIO {
  // свимлейны уровня 1 и колонки уровня 2
  system: SystemCode;
  label: string;
  stage: number;
  direction: 'in' | 'out';
}

interface Stage {
  id: string;
  number: 1 | 2 | 3 | 4;
  title: string;
  shortTitle: string;
  keyOutputs: string[]; // ≤ 4
  warningsCount?: number;
  screen?: ScreenLink;
  groups: Group[];
  nodes: ProcessNode[];
  edges: Edge[];
  inputs: ExternalIO[];
  outputs: ExternalIO[];
}

interface ProcessMap {
  version: string;
  id: string; // 'snp' | 'mrp' — имя каталога src/data/<id>/ и ключ overrides
  updatedAt: string;
  title: string;
  moduleLabel: string; // подпись рамки вокруг потока этапов: «Модуль SNP»
  stages: Stage[];
  overviewEdges: Edge[]; // связи этап→этап и система→этап
}
```

`id` и `moduleLabel` живут в данных, а не в сборке и не в i18n (process-map-3wh.4): обе строки меняются от карты к карте, а ключ `localStorage` выводится из `id` того файла, который реально попал в бандл — тогда содержание, подпись и ключ не могут разъехаться, а выгруженный `process.json` описывает сам себя.

Правила: `id` стабильны (по ним работают deep-link и localStorage); `position` обязателен; инварианты, общие для всех карт, проверяет `tests/mapContract.test.ts`, содержание карты SNP — `tests/snp/` (см. §7).

### Конвейер данных: `npm run data`

`process.json` собирается двумя шагами, и порядок между ними обязателен:

1. `scripts/import-pptx.py` — содержание из презентации; в `position` кладётся **сырая геометрия слайда** (на ней карточки накладываются), её копия — в `slidePosition`;
2. `scripts/layout.ts` (`npm run layout`) — dagre считает по `slidePosition` пригодные координаты и перезаписывает **только** `position`.

Обе половины склеены в одну команду `npm run data`, чтобы порядок не приходилось помнить (`process-map-3b9`). Незавершённый конвейер виден в `npm run check`: `tests/mapContract.test.ts` сверяет координаты файла с пересчётом — для каждой карты.

**Связи между узлами читаются из привязок коннекторов, а не из геометрии** (`process-map-3wh.16`). Долгое время считалось, что в презентации SNP привязок нет; перебор показал обратное — из 66 линий 47 имеют обе привязки `a:stCxn`/`a:endCxn` и лишь 10 не имеют ни одной, импортёр их просто не читал. Привязка точнее: она указывает на фигуру, а не на точку, и не врёт у растянутых коннекторов. Геометрия осталась запасным вариантом для концов, которых привязки не дали. Привязка к **контейнеру** группы разрешается в ближайший шаг этой группы: ребро в модели соединяет узлы, а контейнер узлом не является.

Концы линии вычисляются с учётом **поворота фигуры** (`a:xfrm/@rot`): у повёрнутого коннектора `left/top/width/height` описывают неповёрнутую рамку, и без доворота вокруг её центра концы берутся по чужим координатам. Таких коннекторов 11 в презентации SNP и 3 на слайде 8 презентации MRP — то есть это не редкий случай (`process-map-3wh.18`).

Веерную связь «в группу целиком» один коннектор выразить не может, поэтому `OWNER_DECISION_EDGES` остаётся нужным: линия [146] слайда 5 даёт одно ребро из четырёх, объявленных владельцем.

Карта выбирается флагом: `npm run data -- --map snp`, по умолчанию `snp` (`process-map-3wh.7`). Всё, чем карты различаются, лежит в реестре `MAPS` внутри `scripts/import-pptx.py`: презентация, пути к данным и фикстуре, профиль разбора, заголовок, подпись модуля, дата и отпечаток. Реестр в коде, а не конфигом на диске, потому что тесты уже разбирают исходник импортёра регулярками — Python в CI не запускается. Набор карт продублирован в `scripts/layout.ts::MAP_IDS`, и `tests/mapRegistry.test.ts` сторожит, чтобы два реестра не разошлись: иначе раскладка молча переписала бы координатами не тот файл.

`slidePosition` — служебное поле: в UI не используется, задаёт вход раскладки. Раскладка обязана сидироваться им, а не `position`, который сама же перезаписывает, — иначе после первого прогона она опирается на собственный прошлый результат, а геометрия презентации теряется навсегда (`process-map-cxn`). Поле необязательное: документ без него валиден, раскладка на нём откатывается на `position` и печатает предупреждение.

### Профили разбора презентации

Импортёр умеет два устройства презентации, поле `profile` в `MAPS`:

- **`overview+details`** (карта SNP, «SNP Е2Е процесс.pptx», 6 слайдов) — слайд 2 обзор, слайды 3–6 детализация по этапу. Этап = слайд, группа = контейнер внутри слайда.
- **`single-slide`** (карты MRP, DP, MEIO) — вся карта с одного слайда. **Этап = контейнер**, порядок «верхний ряд, затем нижний слева направо»; `groups` у этапов пустые, потому что группа стала этапом. Контейнер без заголовка — остановка импорта, а не вопрос в отчёт: безымянный этап собирать нельзя.

Реестр карт (`MAPS` в `scripts/import-pptx.py`, `MAP_IDS` в `scripts/mapTarget.ts`; их совпадение сторожит `tests/mapRegistry.test.ts`):

| карта  | профиль            | importer source                        | этапов | адрес раздачи |
| ------ | ------------------ | -------------------------------------- | ------ | ------------- |
| `snp`  | `overview+details` | «SNP Е2Е процесс.pptx», 6 слайдов      | 4      | корень сайта  |
| `mrp`  | `single-slide`     | «In.Plan MRP 17-08-2026.pptx», слайд 8 | 4      | `/mrp/`       |
| `dp`   | `single-slide`     | «In.Plan DP process 06-09-2026.pptx»   | 5      | `/dp/`        |
| `meio` | `single-slide`     | «In.Plan MEIO process 06-09-2026.pptx» | 4      | `/meio/`      |

**Число этапов свободное.** Оно объявлено у карты (`MapSpec.stages_expected`), а не константой на весь импортёр: `StageSchema.number` — `z.number().int().min(1)` с `process-map-70e.4`, и требование «ровно четыре» осталось фактом про конкретную карту (`tests/<map>/content.test.ts`), а не про любую. До карты DP четвёрка ещё жила в импортёре константой `STAGE_COUNT` с устаревшим комментарием «ограничение zod-схемы» и молча не давала собрать пятиэтапную карту.

**Уровни источников** у карт DP и MEIO — четыре, и называть их надо именно так:

- **authoring source владельца** — `scripts/author/<map>.json`. Содержание карты: этапы, шаги, `label`, маркеры, входы и выходы, `keyOutputs`, рёбра, `description`. После согласования заморожено (`CONTENT_FROZEN`);
- **importer source** — сгенерированный из него слайд `In.Plan <MAP> process <дата>.pptx` в корне репозитория (`scripts/author/<map>.py`);
- **runtime source** — `src/data/<map>/process.json`;
- **reference source** — `In.Plan Process Model v11.bpmn`, до миграции source-of-truth (`process-map-70e.15`). Сверка карт с моделью — `docs/reconciliation/dp-meio-bpmn.md`.

**Почему слайд генерируется, а не рисуется руками.** Профиль предъявляет к фигурам требования, которые глазами не видны: заливка ровно `scheme:accent2` у плашек, `noFill` у контейнеров, однострочный заголовок в окне 1 200 000 EMU над контейнером и — главное — **входом считается только плашка с левым краем не дальше 1 828 800 EMU (15 % ширины слайда) от кромки**. Плашка, поставленная «поближе к своему этапу», опознаётся выходом и роняет импорт. Поэтому все входы всех этапов рисуются общей левой колонкой, а до своих шагов идут коннекторами.

**Этот слайд — носитель для импортёра, а не слайд для колоды** (решение владельца от 06.09.2026, отменяет прежнее ожидание «карта и слайд из одного файла»). Из-за общей левой колонки входов часть коннекторов пересекает текст подписей, и без переноса входов это не лечится, а перенос ломает разбор. Слайд для показа людям собирается отдельно и этому конвейеру источником не является.

**`description` и `keyOutputs` у карт DP и MEIO приходят не со слайда**, а таблицами `STEP_DESCRIPTIONS` и `STAGE_KEY_OUTPUTS` — пятой и шестой таблицами решений владельца в импортёре, рядом с `OWNER_DECISION_EDGES`. Причина замерена: у DP этап 2 несёт четыре шага, и прозаические блоки описаний требуют 8,4 млн EMU по высоте при 6,0 млн доступных в контейнере — на слайд они не помещаются, а профиль по определению читает ровно один слайд. Источник правды остаётся один (`scripts/author/<map>.json`), расхождение таблиц с ним ловит `scripts/author/<map>.py` и падает.

Что различается по существу, помимо «где брать этапы»:

|                    | `overview+details`                    | `single-slide`                                                     |
| ------------------ | ------------------------------------- | ------------------------------------------------------------------ |
| входы и выходы     | надписи в левом поле слайда           | автофигуры с заливкой `scheme:accent2` (`is_artifact_box`)         |
| связи «шаг → шаг»  | линии-коннекторы                      | **декоративные стрелки-иконки**: линиями они не нарисованы вовсе   |
| подписи под шагами | `outputs` либо `description`          | `node.inputs` — на слайде это перечни исходных данных              |
| `description`      | подписи внутри контейнера             | таблица `STEP_DESCRIPTIONS` — на слайд не помещаются               |
| `keyOutputs`       | блоки выходов под контейнерами обзора | `data`-узлы с `direction: 'out'`, либо таблица `STAGE_KEY_OUTPUTS` |
| `warningsCount`    | считается                             | не проставляется                                                   |

**Рёбра в профиле `single-slide` собираются из трёх источников в жёстком порядке**: декоративные стрелки → связи внутри этапа; линии с привязками `a:stCxn`/`a:endCxn`, причём привязка к **контейнеру** разрешается в ближайший шаг этого контейнера; линии без привязок — существующим геометрическим разбором. Обе стратегии нужны и именно в этом порядке: единственная линия, которую теряет геометрия (обратная связь, её bbox уходит ниже кромки слайда), — единственная с двумя точными привязками; и наоборот, привязки без геометрии бесполезны, потому что в шести случаях из семи указывают на контейнер.

**Внешние системы** (`stage.inputs`/`outputs` и свимлейны обзора) в профиле `single-slide` выводятся из подписей плашек-артефактов, а не из линий: уровня обзора на слайде нет, но принадлежность известна точно — артефакт лежит в своём этапе и называет свою систему. Направление берётся из происхождения фигуры, потому что `detect_direction` ищет «из модул…»/«в модул…», а на слайде написано «…из SNP, PS». Полные имена модулей отображаются в коды схемы таблицей `SYSTEM_ALIASES` (`SNP → INPLAN`, `MEIO → IO`): владелец уже закрепил эти коды в словаре систем, и заводить вторые коды на те же модули нельзя (`process-map-b67`). Одна подпись может назвать несколько модулей сразу — для этого есть `detect_systems`. Система, не названная в тексте («…в систему исполнения закупок»), **не угадывается**: такой артефакт остаётся `data`-узлом без `ExternalIO`, а импортёр пишет об этом в отчёт.

Направление `data`-узла берётся **по происхождению фигуры**: левое поле слайда — колонка входов. Для плашки вне левого поля правило «значит выход» подкрепляется вторым независимым признаком — она обязана быть целью хотя бы одной связи, иначе импорт останавливается.

### Выбор карты на сборке

Приложение показывает одну карту, но карт в репозитории несколько. Выбор делается **на сборке**, а не в рантайме: роутера и переключателя карт нет, в бандл попадает ровно один JSON, разные карты раздаются с разных адресов (корень — `snp`, подкаталог `/mrp/`).

Единственная точка, где это известно, — `scripts/mapTarget.ts`: реестр `MAP_IDS`, разбор переменной `MAP` и флага `--map`, алиас `@map` на каталог данных, каталог сборки, заголовок карты. `src/data/loader.ts` импортирует `@map/process.json` и не знает, какая это карта; в `src/**` нет ни `process.env`, ни `import.meta.env`, ни ветвлений.

Три вещи, каждая из которых ломается молча и потому зафиксирована явно:

1. **Алиас объявлен в `vite.config.ts` И в `vitest.config.ts`.** Vitest при наличии своего конфига `vite.config.ts` не читает вовсе — заменяет, а не мержит. Алиас только в одном файле даёт зелёный `npm run build` и красный `vitest run`. Оба берут его из `mapAlias()`; инлайнить путь нельзя.
2. **Заголовок вкладки подставляет плагин `inplan-map-title`** из данных карты, а не `document.title` в рантайме (вкладка мигнула бы чужим заголовком, а во view-source остался бы неверный). Плагин **бросает**, если тега `<title>` нет: иначе на странице второй карты молча остался бы заголовок первой. Проверяется в `e2e/maps/smoke.spec.ts`.
3. **`vite build --mode <карта>` использовать НЕЛЬЗЯ.** Vite считает `isProduction` как `(VITE_USER_NODE_ENV ?? mode) === 'production'`, и при кастомном моде `NODE_ENV` в бандле становится `development`: React собирается в dev-режиме, DCE не срабатывает. Сборка при этом «успешна», заметить можно только по размеру, и ни один тест этого не увидит. Карта задаётся переменной `MAP` (через `cross-env` — `MAP=… vite build` не работает в cmd.exe).

Неизвестное значение `MAP` или `--map` роняет команду со списком известных карт: молчаливый откат на карту по умолчанию собрал бы под адресом второй карты первую.

### `direction`: колонки входов и выходов

Колонку data-узла на экране детализации (§4.2) задаёт **явное поле `direction`**, а не координата (`process-map-24p`). Единственный источник правила — `src/utils/stageNodes.ts::splitStageDataNodes`; его читают раскладка, счётчик в крошках и сам экран.

Значение ставит импортёр по **происхождению фигуры**, а не эвристикой: data-узел рождается ровно в двух местах, и каждое знает направление точно — левая колонка входов слайда детализации даёт `'in'`, блок выходов этапа под его контейнером на слайде обзора даёт `'out'`. Поэтому поле стоит у **всех** data-узлов; у остальных типов оно бессмысленно и не проставляется. Ручной правкой это поле не является и в перенос ручных полей (`PRESERVED_NODE_FIELDS`) не входит.

Выводить направление из координат нельзя: блоки выходов этапов 1 и 2 презентация рисует левее середины области шагов, и прежнее правило «левее середины — вход» давало у этих этапов **ноль выходов** при 2–3 ключевых выходах на карточке обзора — экран противоречил сам себе.

Поле необязательное: документ без него (старый файл, экспорт стороннего инструмента, §4.7) остаётся валидным, и такой узел классифицируется прежним геометрическим правилом-фолбэком.

Артефакт, названный выходом этапа в обзоре, но уже существующий узлом колонки входов на слайде детализации, остаётся входом и вторым узлом не заводится — расхождение печатается в отчёте импортёра, а не разрешается за владельца процесса.

### Рёбра по решению владельца процесса

Всё содержание документа читается из презентации. Единственное исключение — `OWNER_DECISION_EDGES` в `scripts/import-pptx.py`: рёбра, которых на слайде нет и которые добавлены **по зафиксированному решению владельца процесса** (`process-map-7bz` — группа «Публикация планов» этапа 3). Дописать их прямо в `process.json` нельзя: импортёр собирает файл с нуля и сотрёт их следующим прогоном (`process-map-2dj`). Объявление в коде переживает перегенерацию по построению и остаётся на виду; отчёт импортёра печатает такие рёбра отдельным блоком, а `tests/snp/importPreserve.test.ts` сверяет объявление с файлом в обе стороны.

### Overrides (localStorage)

Ключ **свой у каждой карты**: `inplan-process-map:<id>:overrides:v1`, то есть `inplan-process-map:snp:overrides:v1` (process-map-3wh.5). Выводится в `loader.ts` из поля `id` той карты, которая попала в бандл, — тогда содержание и ключ не могут разъехаться. Карты раздаются с одного origin, а `localStorage` общий на origin: с единым ключом «Сбросить правки» на одной карте стирал бы черновик другой. Правки, сохранённые под прежним общим ключом `inplan-process-map:overrides:v1`, при первом чтении копируются на ключ SNP; старый ключ не удаляется. Значение `Record<nodeId, { screen?: ScreenLink | null }>`. `loader.ts` накладывает overrides поверх JSON при старте. Экспорт отдаёт полный слитый `process.json`; импорт валидирует zod'ом и заменяет overrides.

Из отредактированного файла импорт переносит **только `screen` у узлов** — это всё, что физически содержат overrides. Молча игнорируются `version`, `updatedAt`, `title`, координаты узлов, рёбра, `stage.screen` и новые узлы: пользователь может отредактировать выгруженный файл и не понять, почему часть правок не приехала (`process-map-m8w`). Решение владельца от 31.08.2026 — оставить как есть, модель overrides не расширять: расширение сломало бы контракт этого же раздела и round-trip, описанный в шапке `src/utils/processTransfer.ts`. Вопрос о предупреждении пользователя вынесен отдельно, вместе с прочими неутверждёнными строками UI (`process-map-ajo`).

`?stage=2` → сразу уровень 2; `&node=<id>` → плюс открытый Drawer. При навигации URL обновляется через `history.replaceState` (не `pushState`, чтобы не ломать историю родительской вики).

### 4.8 Открытие ссылок

`utils/url.ts::openScreen(url)`: `window.open(url, config.linkTarget)`. По умолчанию `linkTarget` = `'_blank'` — экран открывается в **новой вкладке**, страница вики остаётся на месте (решение владельца от 31.08.2026, `process-map-6ap`).

Автоматического выбора цели больше нет. Прежняя редакция требовала целиться в `'_top'` с фолбэком на `'_blank'`, когда `window.top` недоступен, — и фолбэк оказался единственным путём: проба читала `top.document`, а он для чужого origin бросает `SecurityError` всегда, тогда как карта по построению живёт на чужом origin (§6). Доступ к документу верхнего фрейма и право увести этот фрейм — разные вещи, и проба их путала.

`'_top'` остаётся доступен переключением `config.linkTarget`, но только вместе с проверкой на стенде: фолбэка нет, а при `sandbox` без `allow-top-navigation` браузер откажет без исключения.

## 6. Встраивание в In.Plan

```html
<iframe
  src="https://<host>/process-map/?stage=1"
  style="width:100%;height:720px;border:0"
  loading="lazy"
></iframe>
```

**Адрес у каждой карты свой.** `npm run build` собирает обе в один `dist/`: карта по умолчанию (`snp`) в корень, остальные в подкаталог по своему id — то есть MRP встраивается с `https://<host>/process-map/mrp/`. Порядок сборок в скрипте `build` обязателен: сборка карты по умолчанию вычищает `dist` целиком, включая подкаталоги, поэтому идёт первой. Публикация одна на обе карты — промежуточного состояния «новая карта уже есть, старая ещё старая» не бывает.

`vite.config.ts`: `base: './'` — чтобы бандл работал из любого подкаталога. В `dist/` не должно быть абсолютных путей. Сервер не должен отдавать `X-Frame-Options: DENY`; при необходимости `Content-Security-Policy: frame-ancestors https://*.company.ru`.

Атрибут `allow="clipboard-write"` из версии 1.0 убран: в v1 приложение с буфером обмена не работает (`process-map-dps`, проверено grep'ом по `src/`).

Три условия работоспособности, найденные при реализации. Развёрнуто — в `README.md`, там же чек-лист приёмки на стенде.

1. **Завершающий слэш обязателен** (`process-map-phd`). При `base: './'` `index.html` ссылается на `./assets/…` относительно URL документа, поэтому по адресу `/process-map` (без слэша) браузер запросит `/assets/…` в корне хоста и получит 404 — не загрузится сам бандл. Лечится только редиректом 301 на стороне хостинга; требование к хостингу, не к приложению. **Без редиректа отказ у карты в подкаталоге ХУЖЕ, чем в корне.** По адресу `/process-map` браузер запросит `/assets/…` и получит 404 — страница останется пустой, дефект очевиден. По адресу `/process-map/mrp` он запросит `/process-map/assets/…`, а этот путь существует: загрузится бандл СОСЕДНЕЙ карты под заголовком запрошенной. Отказ не пустая страница, а чужая карта, и заметить его можно только глазами.
2. **`sandbox` без `allow-popups` не даёт открыть экран** (`process-map-6ap`). Ссылка открывается в новой вкладке (§4.8), и заблокированный `window.open` возвращает `null` — отказ наблюдаем, в отличие от прежнего тихого отказа `_top`-навигации. Требование к встраивающей стороне: либо без `sandbox`, либо с `allow-popups`, `allow-scripts`, `allow-same-origin` (без последнего недоступен `localStorage` для overrides §3, но сама карта работает) и `allow-downloads` (иначе молча не сработает «Экспорт JSON», §4.4). Проверяется в `e2e/iframe-sandbox.spec.ts`.
3. **Только https** (PRD §9): http-фрейм в https-вики блокируется как mixed content.

## 7. Тестирование

Корпус разделён по одному признаку: можно ли направить проверку на другую карту и ожидать зелёного (process-map-3wh.3).

- `tests/loader.test.ts` — merge overrides, импорт/экспорт round-trip.
- `e2e/maps/smoke.spec.ts` — смоук, гоняется для каждой карты: обзор грузится, четыре карточки, подпись рамки из `e2e/maps/expected.ts`, переход на уровень 2 и возврат крошкой.
- `e2e/` (вне `maps/`): обзор → этап 2 → шаг → Drawer → «Открыть в модуле» (перехват `window.open`); редактор: сохранить ссылку, перезагрузить, ссылка на месте; компактный режим при viewport 1024×600. Содержат подписи и id узлов SNP дословно, поэтому гоняются только для карты по умолчанию.
- `npm run check` = typecheck + lint + unit; `npm run e2e` отдельно.

## 8. Definition of Done для задачи

Код + тесты зелёные (`npm run check`) + при UI-задаче скриншот Playwright сравнён глазами с соответствующим артбордом + `bd close <id> "…"` с кратким описанием.
